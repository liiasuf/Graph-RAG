# GraphRAG - графы знаний поверх векторных индексов

Научно-исследовательская работа 1 курса: **GraphRAG - построение и использование графов знаний поверх индексов**.

## О проекте

Сравнение RAG и трёх GraphRAG методов на 5 вопросно-ответных
бенчмарках (многошаговых и одношаговых), на 3 LLM, n=500 вопросов на
датасет, граф - Neo4j:

| Система | Стратегия извлечения |
|---------|----------------------|
| **`vector`** (RAG-baseline) | Поиск ближайших соседей по косинусному сходству эмбеддингов BGE-M3 |
| **`graph_only`** | Кандидаты берутся исключительно из графа совместной встречаемости сущностей - векторного дополнения нет |
| **`graph_overlay`** | Vector top-k задаёт базовый набор (floor), граф добавляет к нему кандидатов, после чего всё объединяется и пересортировывается по косинусной близости |
| **`graph_rerank`** | Новых кандидатов граф не добавляет - он только меняет порядок вектороного пула, основываясь на расстоянии по хопам в графе |

Все результаты, выводы -
`experiments/paper_results.md`. Коротко - см. раздел
[«Ключевые выводы»](#ключевые-выводы) ниже.

## Архитектура

### Индексирование

```
Документы
   │
   ▼
Чанкинг
   │
   ▼
BGE-M3 (эмбеддинги)
   │
   ├──────────────────────┬──────────────────────┐
   ▼                      ▼                      ▼
NumpyCosineIndex     ChunkMapping         Neo4jGraphIndex
float32-векторы      (mapping.json)       граф совместной встречаемости
embeddings.npy       row → {chunk_id,     (Neo4j, персистентный)
                       title, text}       entity → chunk_ids
                                           тег: experiment=<name>
                                           используется только в:
                                           graph_only / graph_overlay /
                                           graph_rerank
```

### Извлечение

```
vector
──────
запрос → embed → cosine search → top-k строк → mapping.lookup() → LLM


graph_overlay / graph_only
───────────────────────────
запрос ─┬─ embed → cosine search (нижний порог, только overlay) ─┐
         │                                                        │
         └─ NER → обход графа в Neo4j → кандидаты → cosine re-rank┘
                                                        │
                                                     merge → LLM


graph_rerank
────────────
запрос → embed → cosine search → vector-пул
                                     │
                    граф пересчитывает score
                    по hop-расстоянию до seed-сущностей запроса
                                     │
                                  top-k → LLM
```

**Важно:** `NumpyCosineIndex` хранит только векторы (числа) и ничего больше. `ChunkMapping` (`mapping.json`) хранит только тексты чанков. Эти два хранилища никогда не смешиваются — векторы не лезут в mapping, а тексты не лезут в индекс векторов.

## Быстрый старт

```bash
# 1. Установка
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev,neo4j]"

# 2. Конфигурация
cp .env.example .env

# 3. Neo4j (нужен для всех режимов кроме vector)
docker-compose up -d

# 4. Базовый запуск (RAG)
python run_e2e.py --config configs/e2e_hotpotqa.yaml

# 5. Запуск GraphRAG (любой Neo4j-режим - один и тот же скрипт)
python run_e2e_graphrag_neo4j.py --config configs/e2e_hotpotqa_graph_rerank.yaml

# 6. Сравнение результатов
python compare_runs.py

# 7. Полный прогон: 5 датасетов x 4 системы x 3 LLM, n=500/датасет
python run_model_sweep.py --quick                 # сначала быстрый тест на маленьком корпусе
python run_model_sweep.py                         # затем полный прогон 
python run_model_sweep.py --skip-existing         # пересчитать только недостающие комбо (или если что-то упало)

# 8. Отчёт по результатам полного прогона
python run_rq_experiments.py
```

## Метрики

| Метрика | Описание |
|---------|---------|
| **EM** (Exact Match) | Ответ модели считается правильным только если он дословно совпадает с эталонным (после приведения строки к единому виду — например, без учёта регистра и пунктуации) |
| **F1** | Сравнивает ответ модели с эталоном не целиком, а по отдельным словам — считает, сколько слов общие, и даёт более мягкую оценку, чем EM, если ответ верный по смыслу, но сформулирован иначе |
| **ROUGE-L** | Похож на F1, но учитывает ещё и порядок слов — ищет самую длинную общую последовательность слов между ответом модели и эталоном |
| **Recall@k** | Из всех документов, которые действительно нужны для ответа, какая доля попала в первые k найденных системой документов — показывает, насколько хорошо система «не теряет» нужные источники |
| **Precision@k** | Из k документов, которые система выдала как топовые, какая доля оказалась действительно нужной — показывает, насколько система не «замусоривает» результат лишним |
| **MRR** | Насколько высоко в списке найденных документов оказался первый по-настоящему нужный документ — чем выше он стоит, тем выше метрика |
| **NDCG@k** | Учитывает не только то, что нужные документы найдены, но и на каком именно месте они оказались — чем ближе к началу списка, тем больше «вес» получает документ |
| **Галлюцинации** | Доля слов в ответе модели, которых не было ни в одном из найденных фрагментов текста — показывает, насколько модель «придумывает» информацию от себя, а не опирается на найденные данные |

## Режимы `retrieval.mode`

| `retrieval.mode` | Что делает | Backend графа | Нужен Neo4j? |
|---|---|---|---|
| `vector` | Обычный поиск ближайших по смыслу фрагментов через косинусное сходство эмбеддингов (базовый вариант RAG, без графа) | — | нет |
| `graph_neo4j` | Система обходит граф связей между сущностями, находит кандидатов, дополнительно пересортировывает их по косинусному сходству — при этом обычный векторный поиск (top-k) выполняется всегда и используется как основа | Neo4j | **да** |
| `graph_neo4j_only` | Используются только кандидаты, найденные через граф, — векторный поиск ничего не добавляет. Если граф вообще не смог найти кандидатов, система откатывается на обычный векторный поиск, и этот случай отдельно фиксируется в логах как `fallback_used` | Neo4j | **да** |
| `graph_neo4j_rerank` | Граф не ищет новых кандидатов, а только меняет порядок уже найденных: сначала обычный векторный поиск отбирает пул кандидатов (размер задаётся параметром `vector_pool_k`), а затем граф пересортировывает их по тому, насколько «близко» они расположены (по числу связей-переходов) к сущностям из запроса | Neo4j | **да** |

Для всех режимов кроме `vector` нужен запущенный Neo4j:

```bash
docker-compose up -d
pip install -e ".[neo4j]"

# любой из Neo4j-режимов - один и тот же оркестратор, выбор по retrieval.mode в конфиге
# конфиг называется по методу: graph_overlay / graph_only / graph_rerank / adaptive
python run_e2e_graphrag_neo4j.py --config configs/e2e_hotpotqa_graph_overlay.yaml  # graph_neo4j (наложение)
python run_e2e_graphrag_neo4j.py --config configs/e2e_hotpotqa_graph_only.yaml     # graph_neo4j_only (чистый граф)
python run_e2e_graphrag_neo4j.py --config configs/e2e_hotpotqa_graph_rerank.yaml   # graph_neo4j_rerank
python run_e2e_graphrag_neo4j.py --config configs/e2e_hotpotqa_adaptive.yaml       # adaptive (свой метод)
```

`adaptive` (`AdaptiveMethodConfig` в `config.py`) собирается из трёх независимо
включаемых частей, каждая проверяется отдельной группой абляций в
`run_ablations_full.py`:

| Компонент | Конфиг | Абляция |
|---|---|---|
| Router (пропуск графа) | `adaptive.router.enabled/method/min_entities_for_graph` | `B1_router` |
| Граф-реранкер | `adaptive.graph_retrieval_mode` (переиспользует `graph_neo4j`/`graph_neo4j_only`/`graph_neo4j_rerank`) | `B2_graph_rerank` |
| Subquestion-декомпозиция | `adaptive.subquestions.enabled/max_iterations/sufficiency_check` | `B3_subquestions` |

```bash
python run_ablations_full.py --group B1_router
python run_ablations_full.py --group B4_combined   # все три части вместе
```

## Ключевые выводы

Полная версия с таблицами по каждому исследовательскому вопросу — в `experiments/paper_results.md`.
Все цифры ниже получены на полных e2e-прогонах (5 датасетов × 4 системы × 3 LLM,
n=500 вопросов на датасет, корпус текстов без урезки).

- **Гипотеза «граф сильнее помогает там, где нужно рассуждать в несколько шагов» не подтвердилась.**
  «Шаг рассуждения» — это переход от одного факта к другому,
  который нужен, чтобы дойти до ответа (например: сначала найти, в каком городе родился человек,
  потом — в какой стране этот город находится). Ожидалось, что чем больше таких шагов в вопросе,
  тем сильнее граф связей между сущностями должен помогать retrieval'у по сравнению с обычным
  векторным поиском. На практике на многошаговых датасетах (HotpotQA, MuSiQue, 2WikiMultiHop)
  прирост `graph_rerank` над обычным `vector` оказался незначительным (+0.5–1.9 процентных пункта
  по метрике Recall@8 — доле нужных документов, попавших в первые 8 найденных).
  Самый большой эффект неожиданно проявился на **Natural Questions** — датасете с
  **одношаговыми** вопросами, где ответ и так лежит в одном фрагменте текста: там Recall@8
  вырос на 41 п.п., точное совпадение ответа (EM) — на 16.6 п.п., а доля «придуманных» моделью
  фактов (галлюцинации) упала с 38.6% до 6.6%. На TriviaQA (тоже одношаговом датасете) граф
  почти ничего не изменил. Вывод: то, насколько граф помогает, зависит от особенностей
  конкретного датасета и структуры его корпуса, а не от количества шагов рассуждения в вопросе.

- **Порядок систем по качеству одинаковый на всех трёх проверенных LLM:**
  `graph_rerank` ≥ `graph_overlay` > `vector` ≫ `graph_only` — независимо от того,
  какая языковая модель использовалась для генерации ответа. Это говорит о том, что разница
  между архитектурами retrieval'а — системный эффект, а не случайность, связанная с одной
  конкретной моделью.

- **У `graph_overlay` есть математическое ограничение: он никогда не может оказаться хуже `vector`**,
  потому что список кандидатов от обычного векторного поиска (top-k) всегда является
  подмножеством его собственных кандидатов — иначе говоря, `graph_overlay` строится поверх
  `vector` и включает его результаты как часть своих. Из-за этого в основных таблицах в роли
  «GraphRAG» показан именно `graph_rerank`, а не `overlay` — иначе сравнение свелось бы, по сути,
  к сопоставлению `vector` с самим собой.

- **Построение графа не замедляет ответ системы.** Сам граф строится один раз офлайн, и это
  занимает от 2 секунд (для NQ) до примерно 5 минут (для HotpotQA, где в графе 325 тысяч
  сущностей) — это разовые затраты на подготовку, а не на каждый запрос. Время ответа на
  сам вопрос при использовании графа сопоставимо с обычным RAG или даже быстрее, потому что
  основное время уходит на генерацию ответа языковой моделью, а не на обход графа.
